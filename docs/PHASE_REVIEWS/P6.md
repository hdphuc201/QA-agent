## Implementation summary

- **T01** Sample app `examples/sample-app/`, built in P2 (ADR 0004): requester/approver/viewer, an approval workflow, seed data, a test-mode reset, an opt-in defect and requirements with IDs. A requirement for the multi-tab flow (DEMO-REQ-APP-004, fixture data) was added.
- **T02** `scripts/smoke/vertical-slice.mjs` runs the pipeline on a fresh copy of the sample app started from seed data: `discover` (live via Playwright MCP, signed in) → `plan` → `generate --validate` → `run` (scheduler). Every run now freezes its inputs (project map, observations, plan, case map, generated manifest) plus `versions.json` (QA Agent version, plan schema version, generated plan hash) under `qa-artifacts/runs/<runId>/inputs/`.
- **T03** 20 READY cases ran: happy 4, negative 3, boundary 4, RBAC 8, state transition 3. Two NEEDS_REVIEW cases are not run, which is correct. No filler cases were added.
- **T04** Two roles with separate contexts, plus a second tab of the requester's context. The requirement language gained `… in a second tab`; the generator emits `actors.newTab(role)`. The runner is non-interactive (`qa-agent run`, Playwright only; no AI per click).
- **T05** Intentional defect `SAMPLE_APP_BUG=skip-approve-rbac` (the server stops checking who may approve). Exactly the two API authorization cases failed: DEMO-REQ-APP-003-002/004, "Expected: 403, Received: 200". The UI cases (no "Approve" button) still passed, which shows that hiding a button is no proof of authorization (§7.2). The defect is env-only; the next run without it passed 20/20.
- **T06** Three clean runs (fresh copy + fresh app each time): 20/20 each, no flaky or failed test. The plan hash and the generated specs are identical across all runs.
- Version alignment: `package.json` is 0.1.0 (= plugin manifest).

## Gate criteria

- Vertical slice succeeds on the sample app with Playwright specs, logs and artifacts: yes (3 clean runs).
- The intentional bug is really detected: yes, by exactly the cases that check it, with the HTTP mismatch in the error.
- At least 2 contexts and meaningful business assertions: requester/approver/viewer contexts plus a second tab; status transitions, 401/403/400 responses, persistence (list count), validation messages.
- 3 runs with complete stored results: `evidence/P6/slice-clean-{1,2,3}`.

## Defects found and fixed

- `package.json` version (0.0.0) did not match the plugin manifest (0.1.0); this showed up in the first `versions.json`.
- No product or test defects surfaced in P6 runs. Test counts changed only because the fixture requirements gained DEMO-REQ-APP-004 (planner 22 cases/20 READY, generator 20, scheduler 19 + 1); goldens were regenerated and reviewed.

## Security checks

The evidence was redacted (`<HOME>`) and scanned: no user names, no credentials (demo values are only in the local fixture and scripts). Session files were purged after every run.

## Remaining risks

- The slice uses a demo app built for this project. Real-world apps (CHUNJI) need requirements in the controlled format and a configured login recipe.
- Error messages in JSON results contain ANSI colour codes (handled by P7 normalisation).
- Browser: installed Chrome channel; Chromium/CI in P9.
- Skills inside Claude Code are still to be exercised by the owner (P7).

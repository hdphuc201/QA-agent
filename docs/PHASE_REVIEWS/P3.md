## Implementation summary

- **T01** `src/planning/schema.ts`: Zod contracts (schemaVersion 1) for `Requirement`, `TestScenario`, `TestCase`, `TestPlan`. A case has a stable ID, requirementRefs, actors (role + accountKey), preconditions, structured setup/steps, expectations (verbatim requirement sentence + file:line + structured assertions), category, priority, riskScore, status, dependencies, blockers, provenance and an automation slot.
- **T02** `src/planning/requirements.ts`: parses requirement docs in a controlled format (`docs/REQUIREMENTS_FORMAT.md`), links each requirement to the project-map routes/UI it mentions and lists routes no requirement covers. Expected results come only from `Expected` lines; code/observations add links and gaps, never expectations.
- **T03** `src/planning/interpret.ts` + `planner.ts`: a rule-based interpreter (no AI) turns Given/When/Expected sentences into steps/assertions. The project map resolves link → form → submit button. Unknown sentences become `manual`. Matrix generation covers happy, negative, boundary (one case per value), RBAC (per actor; API 401/403 split), state transition; network-failure/concurrency cases appear only when required (none in the demo, reported as "not required").
- **T04** Deduplication by behaviour + expected outcome (refs merged, highest priority kept); risk = impact(priority) × likelihood(category) → P0/P1/P2; dependencies come from "Given: a <status> <thing> created by <role>" → the producing case becomes setup; cycle detection; transitive BLOCKED.
- **T05** Statuses: DRAFT (initial) → READY only if every step and assertion is machine-checkable; NEEDS_REVIEW for missing or manual expectations; BLOCKED for missing roles, producers or dependency problems. `runnableCases()` returns READY only.
- **T06** `src/planning/{export,plan-stage}.ts` + `qa-agent plan`: `.qa-agent/plan/test-plan.json` (versioned), `test-plan.md` (review view quoting requirement lines) and `test-cases.csv`. The `plan` skill now calls the engine.
- Sample requirements were tightened to the controlled format (fixture data; e.g. REQ-003 now states its When and per-label expectations).

## Test evidence (gate criteria)

- **Reasonable case groups with grounded assertions:** `tests/unit/planner.test.ts` checks category and status counts, boundary cases, the two-role workflow with dependency, and that every expectation quotes an existing requirement line (file:line) with matching `requirementRefs`.
- **Missing expected result → NEEDS_REVIEW, no simulated result:** REQ-004 (no Expected), unmeasurable sentences (`manual`), and network-failure text without an automatable condition are all NEEDS_REVIEW; `runnableCases` excludes them (`plan-status.test.ts`).
- **Duplicates and dependency cycles:** `tests/unit/plan-dedupe.test.ts` covers duplicates merged with both refs and the highest priority, non-duplicates kept, a cycle → BLOCKED with the cycle path, transitive BLOCKED, a missing producer → BLOCKED and a missing role → BLOCKED.
- **Invalid inputs:** `plan-schema.test.ts` (schema violations) and `plan-export.test.ts` (duplicate requirement IDs, corrupt project map, missing plan; CSV/Markdown escaping).
- **Regression:** P0–P2 suites green. Changing the P2 explorer for the flakes below re-ran the full suite 3×.

## Defects found and fixed during the phase

1. The interpreter left the approver filling "Reason" without opening the request → rule added: with a subject, a role's first action happens on the subject page. Documented in the format doc.
2. Merged duplicates kept the lower priority → now keep the highest. A test assertion was added.
3. Split API cases for 401/403 were categorised as `negative` → now `rbac`.
4. Live-test flakes under the full parallel suite (P2 code): a redirect reported as "interrupted navigation" (my first fix also wrongly accepted a `chrome-error://` target; the next full run caught it), and browser launch exceeding 30 s under load. Fixed with unit tests. The full suite then passed 3/3.
5. A test expectation of mine miscounted categories (rbac 8 / negative 3 verified by hand against the rules) and was corrected. No product expectation was changed to make a test pass.

## Security checks

Planning reads only `docsPaths` (through the safe reader) and writes only `.qa-agent/plan/`. No credentials appear in plans (actors carry `accountKey` only). Evidence logs were redacted (`<HOME>`). No real secrets in changed files.

## Remaining risks

- The controlled language is deliberately narrow. Real-world requirement documents (e.g. CHUNJI) will need authoring in this format or produce mostly NEEDS_REVIEW. An AI-assisted rewrite would need owner approval, and the plan skill forbids silent edits.
- Some assertions are page-level text checks (e.g. "Pending" anywhere on the list page). Row-scoped checks are a P4 generator concern.
- A plan without a project map degrades to 6 READY / 19 cases (honest, but `discover` is effectively required first).
- Symlink test still unexecuted on Windows (1 skipped).
- Skills `discover` and `plan` have not yet been invoked inside Claude Code by the owner (planned with the full pipeline in P7).
